# Reports

Generated by `src/daily_brief.py` on ctihermes. Deterministic Python owns all
Elasticsearch aggregation; the LLM (Hermes `rawingest` profile — no memory, no
skill authoring, no OpenCTI tools) only narrates the pre-aggregated evidence.

Reports are written to `/home/mike/reports/` on the VM. **Nothing is
auto-committed** — the agent has no GitHub credentials by design (a scheduled
job that reads attacker-controlled text and can push to a repo is a
prompt-injection path to durable contamination). Reports land here only after
a human reviews them.

Raw evidence JSON for each run stays on the VM at
`/home/mike/reports/evidence/YYYY-MM-DD.json`.

## Known accuracy issues (first run, 2026-08-03)

The deterministic evidence was correct; the LLM narration introduced errors.
This is exactly why the peer review called for an eval loop. Observed:

- **Sensor mischaracterization**: called Beelzebub "IRC Botnet C&C" — it is an
  LLM-based SSH/HTTP honeypot. The SOUL.md glossary needs Beelzebub and
  Heralding entries.
- **Arithmetic**: claimed the top 4 IPs were "38% of aggregate events"; the
  evidence gives ~27%.
- **Identifier corruption**: `CVE-2020-11900` restated later as
  `CWE-2021-11900`.
- **Internal inconsistency**: described the empty password as having a "high
  count" (60) while listing `123456` above it at 220.
- **Miscount**: "Top 6 IP addresses" over a 4-row table.

Fixes to make before this runs unattended: expand the sensor glossary, compute
percentages in Python and pass them in as evidence rather than letting the
model do arithmetic, and validate CVE identifiers against the evidence JSON.
